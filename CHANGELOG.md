# Changelog

## [Unreleased]

### Fixed

- `SipCredential`: importing a credential no longer warns "One or more imported inputs failed to validate". Twilio never returns the password, so the imported inputs have an empty one and `Check` rejected it; an empty password is now accepted by `Check` (a non-empty one shorter than 12 characters still fails), while `Create` and `Update` refuse an empty password with `password must be set`. The in-place password update planned after an import is expected and documented. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/9 (#1635).
- `VerifyService`: removing `totpIssuer` from the program no longer fails with HTTP 400. Twilio sets the issuer to the friendly name at creation and rejects an empty value, so a removed input now leaves the issuer unchanged (like `defaultTemplateSid`); the description said it cleared the issuer. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/8 (#1633).
- Import no longer adopts Twilio's string defaults into the inputs: `MessagingService.usecase` equal to `undeclared` and `VerifyService.totpIssuer` equal to the friendlyName are left out, so `pulumi import` followed by `preview --expect-no-changes` plans nothing for a program that sets only the required fields. A different value is still adopted. The import-only map is separate from the update-reset maps. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/2 (#1634).
- `EventSink`: a Segment sink sent its write key as `key`, which Twilio rejects; it is now sent as `write_key` (and Twilio's `sink_configuration.write_key` is what a refresh reads). Twilio returns the webhook `method` in lower case (`post`), so a refresh and an import now read it as upper case and `webhookMethod` is compared case-insensitively: an imported default-method sink no longer adopts `webhookMethod: post` and a sink with a non-default method (`GET`) no longer plans a replacement after import. The test fake now rejects configuration keys unknown to the sink type and lower-cases the method like Twilio. Mirror issues https://github.com/pulumi-labs/pulumi-twilio/issues/6 and https://github.com/pulumi-labs/pulumi-twilio/issues/7 (#1631, #1632).
- If the provider schema cannot be loaded during a `Read`, the failure is no longer cached for the life of the process: the next `Read` retries (#1599). The lookup functions were audited: none returns a credential value, so no function output changes.

### Added

- New resources `Trunk`, `TrunkOriginationUrl`, `TrunkCredentialList` and `TrunkIpAccessControlList` for Elastic SIP Trunking (trunking.twilio.com), with lookups `getTrunk`, `getTrunkOriginationUrl`, `getTrunkCredentialList` and `getTrunkIpAccessControlList`. A `Trunk` manages `domainName` (`<name>.pstn.twilio.com`), `friendlyName`, the disaster recovery URL and method, `transferMode`, `transferCallerId`, `secure`, `cnamLookupEnabled` and the recording settings `recordingMode` and `recordingTrim` (applied through Twilio's Recording sub-resource); everything updates in place and the `effective` output shows what Twilio holds. A `TrunkOriginationUrl` (`sipUrl` must be a `sip:` URL; `weight` and `priority` default to 10, `enabled` to true) updates in place and only `trunkSid` replaces it. `TrunkCredentialList` and `TrunkIpAccessControlList` attach an existing `SipCredentialList` or `SipIpAccessControlList`; Twilio has no update call, so every input replaces, and destroy only detaches. Trunks belong to the credentials' account (no `accountSid`). Phone numbers keep being attached with `IncomingPhoneNumber.trunkSid`. Import IDs: `Trunk` by SID, the others as `<trunkSid>/<sid>`; an imported trunk adopts only settings that differ from Twilio's defaults, so omitting a setting or stating its default plans no change. Shapes follow twilio-oai `twilio_trunking_v1.json`; mocked-HTTP tests only.

- New resources `EventSink` and `EventSubscription` for Twilio Event Streams, with lookups `getEventSink` and `getEventSubscription` (both by `sid`). A sink is a `webhook` (`webhookDestination`, `webhookMethod`, `webhookBatchEvents`), `kinesis` (`kinesisArn`, `kinesisRoleArn`, `kinesisExternalId`) or `segment` (`segmentWriteKey`) destination; only its `description` updates in place and every other input replaces, because Twilio's API cannot change a sink's configuration. `segmentWriteKey` and `kinesisExternalId` are secrets, and Twilio does not return the write key, so drift in it is not detected. A subscription takes a `description`, a `sinkSid` (replaces) and a list of `types` (`type`, optional `schemaVersion`); types are added, re-versioned and removed in place through the SubscribedEvents endpoints, and a refresh picks up types changed outside Pulumi. Twilio only creates a subscription for an active sink: a new sink must be validated first (Twilio's sink test and validate calls, which are not part of the provider). Import by SID; an imported sink never replaces because of a setting Twilio does not return (the Segment write key, a missing Kinesis external ID) or states as a default (`webhookMethod` `POST`, `webhookBatchEvents` false); an imported subscription pins the schema version of every type. Shapes follow twilio-oai `twilio_events_v1.json`; mocked-HTTP tests only.

- New resources `ShortCode` (SMS webhooks, `friendlyName`, `apiVersion` of a leased short code), `ConnectApp` (listing details and `permissions` of a Console-created Connect app) and `OutgoingCallerId` (the `friendlyName` of a verified caller ID), with lookups `getShortCode` (by `code` or `sid`), `getConnectApp` and `getOutgoingCallerId` (by `phoneNumber` or `sid`). Twilio's REST API cannot create a short code, cannot create a Connect app, and verifies a caller ID by phoning the number, so all three adopt an existing object (like `IncomingPhoneNumber`) and destroy leaves it in place without an API call. `accountSid` (a subaccount) replaces, because the API has no way to move these objects; subaccount import IDs are `<accountSid>/<sid>`. Removing `ConnectApp.companyName`, `description`, `homepageUrl`, `authorizeRedirectUrl` or `permissions` leaves the value on Twilio (the Console form requires them); removing a webhook URL clears it and a method goes back to `POST`. Shapes follow twilio-oai `twilio_api_v2010.json` (`SMS/ShortCodes`, `ConnectApps`, `OutgoingCallerIds`); mocked-HTTP tests only.

- New resources `SipDomainCredentialListMapping` (`authScope` `calls`, the default, or `registrations`) and `SipDomainIpAccessControlListMapping`, with lookups `getSipDomainCredentialListMapping` and `getSipDomainIpAccessControlListMapping`. They map a credential list or an IP access control list to a SIP domain, so `SipDomain.authType` is now managed through them. Twilio has no update call on a mapping, so every input replaces. IDs: `<domainSid>/<authScope>/<sid>` and `<domainSid>/<sid>` (`<accountSid>/` prefix in a subaccount); the `sid` is the mapped list's SID. The legacy `Domains/{sid}/CredentialListMappings` paths are not used: they alias the `Auth/Calls` mappings. Shapes follow twilio-oai `twilio_api_v2010.json`; mocked-HTTP tests only.

- New resources `Address` (customer postal address; `isoCountry` replaces, `autoCorrectAddress` is write-only), `SigningKey` (secret returned once, stored as a secret), `Queue` (`friendlyName`, `maxSize`, with live `currentSize` and `averageWaitTime` outputs) and `UsageTrigger` (only `callbackUrl`, `callbackMethod` and `friendlyName` update in place), each with an optional `accountSid`, subaccount import by `<accountSid>/<sid>` and a lookup function (`getAddress`, `getSigningKey`, `getQueue`, `getUsageTrigger`). Removing `Queue.maxSize` resets it to Twilio's documented default of 1000. Shapes follow twilio-oai `twilio_api_v2010.json`; mocked-HTTP tests only.

- New SIP resources `SipCredentialList`, `SipCredential`, `SipIpAccessControlList`, `SipIpAddress` and `SipDomain`, each with an optional `accountSid` (replaces) and a lookup function (`getSipCredentialList`, `getSipCredential`, `getSipIpAccessControlList`, `getSipIpAddress`, `getSipDomain`). Import IDs: the lists and the domain by bare SID, `SipCredential` and `SipIpAddress` by `<listSid>/<sid>`, and `<accountSid>/<sid>` or `<accountSid>/<listSid>/<sid>` in a subaccount. `SipCredential.password` is a secret input and output that Twilio never returns: drift is not detected and an imported credential gets its password on the next `pulumi up` (in place). `SipIpAddress.cidrPrefixLength` resets to 32 when removed. `SipDomain.domainName` updates in place; mapping credential lists and IP access control lists to a domain is not managed yet, so `SipDomain.authType` is read-only. Shapes follow twilio-oai `twilio_api_v2010.json`; mocked-HTTP tests only, not run against a live Twilio account.

- `Application` gains `apiVersion` and `publicApplicationConnectEnabled`; `IncomingPhoneNumber` gains `trunkSid`, `voiceReceiveMode`, `addressSid`, `identitySid`, `bundleSid`, `emergencyStatus`, `emergencyAddressSid` and `apiVersion`; `MessagingService` gains `usecase`. They update in place and show up in the `effective` output. Removing a SID reference unassigns it; removing `apiVersion`, `voiceReceiveMode`, `emergencyStatus` or `usecase` leaves the value on Twilio unchanged.
- `VerifyService` gains `defaultTemplateSid` (validated as an `HJ` SID when known), `verifyEventSubscriptionEnabled` and the push, TOTP, WhatsApp and passkeys settings as flat fields: `pushApnCredentialSid`, `pushFcmCredentialSid`, `pushIncludeDate`, `totpIssuer`, `totpCodeLength`, `totpTimeStep`, `totpSkew`, `whatsappMsgServiceSid`, `whatsappFrom`, `passkeysRelyingPartyId`, `passkeysRelyingPartyName`, `passkeysRelyingPartyOrigins`, `passkeysAuthenticatorAttachment`, `passkeysDiscoverableCredentials` and `passkeysUserVerification`. Twilio's OpenAPI definitions do not type the nested response objects, so their key names are inferred from the request parameters and not yet verified against a live account.

### Fixed

- Security: `pulumi import` and `pulumi refresh` now store the properties this provider marks secret (`ApiKey.secret`, `SigningKey.secret` and `Subaccount.authToken`) as secrets. A `Read` response only kept the secretness of the state it was given, and an import has no state, so a value the provider recovered from the API was written to the state as plaintext. The secret properties are read from the provider's own schema, so every resource is covered. State imported before this fix stays plaintext until its next `pulumi refresh`, which re-encrypts it (#1577).
- A preview no longer invents resource IDs. `Create` during `pulumi preview` returned the resource's logical name (or the placeholder `preview`) as its ID, so `id` was a known, wrong value and a program passing it to a lookup or to another resource ran against a name that does not exist and failed the preview (for example `getWebhook(webhook.id)`). A preview has no real ID now, so `id` stays unknown until the apply. Mirror issue https://github.com/pulumi-labs/pulumi-huggingface/issues/7 (#1590).
- Changing the provider configuration (a rotated token, API key or secret, a new endpoint or region) is an in-place update of the default provider. By default pulumi-go-provider replaced the provider on any config change, and replacing a provider replaces every resource that uses it, so rotating a credential would have deleted and recreated every resource. Each resource's own diff still decides whether it changes. Mirror issue https://github.com/pulumi-labs/pulumi-huggingface/issues/8 (#1591).
- `ApiKey`: the documented restricted-key policy was not a policy Twilio accepts. `{"allow":["/v1/Services/**"]}` (the schema description, SKILLS.md and, as `/v2/Services/**`, the six `twilio-subaccount` examples) fails with error 70002; Twilio only takes assertions of the form `/twilio/<product>/<resource>/<action>`, and the verified example is now `{"allow":["/twilio/iam/api-keys/create"]}` everywhere. Check logs a warning for an assertion that does not start with `/twilio/`.
- `ApiKey`: a failed create no longer leaves an untracked key. Twilio creates the key and then fails the call with 70002, and the error carries no SID, so the key was a live credential Pulumi did not know about. Create now notes the account's keys before the call and, on failure, deletes the key that is new and carries this resource's friendly name (never a key that existed before); if the keys cannot be listed (including an account with more keys than the 10 pages it reads) or the key cannot be deleted, the error says so and names what to look for. Every `ApiKey` create now costs one extra key listing, and a failed create removes keys of its friendlyName created during the call, so keep friendlyNames unique among keys created in one program. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/4 (#1574).
- Previewing an update no longer makes identifiers unknown. A preview that only renamed a `Subaccount` marked its `sid`, `ownerAccountSid` and auth token unknown, so every resource reading `${sub.sid}` into its `accountSid` (which replaces) was planned for replacement, although the real update is in place; replacing a subaccount `ApiKey` would have lost its one-time secret, so the preview misled anyone reviewing it. Every resource now declares what its outputs derive from: identifiers fixed at creation (`sid`, `ownerAccountSid`, `dateCreated`, `secret`, `authToken`, ...) stay known on update, while what Twilio reports and can change (`effective`, queue counters, address validation, usage values) stays unknown. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/3 (#1573).
- Import no longer adopts Twilio's own defaults as inputs. `Application`, `MessagingService`, `VerifyService` (and every other resource that adopts on import) copied each returned flag or number into the inputs unless its default was verified, so `pulumi import` followed by a program that set only `friendlyName` planned to remove `voiceCallerIdLookup`, `stickySender`, `codeLength`, `psd2Enabled` and the like, and failed `--expect-no-changes`. A flag or number is now adopted only when Twilio's OpenAPI states its default and the returned value differs from it; the others stay out of the inputs and remain visible in the `effective` output. Trade-off: this also leaves out a genuine non-default setting of such a field (for example `codeLength: 4` or `stickySender: false`), so `pulumi import --generate-code` omits it; the setting is still shown in `effective`, and declaring it in the program is an ordinary in-place update that sends the declared value. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/2 (#1572).
- Import now adopts a non-default flag or number even when Twilio's OpenAPI states no default (#1595). An import-only default map holds the values a fresh resource reports on the live API (`voiceCallerIdLookup` false, `stickySender`, `areaCodeGeomatch`, `mmsConverter`, `smartEncoding` and `dtmfInputRequired` true, `synchronousValidation`, `useInboundWebhookOnNumber`, `customCodeEnabled`, `psd2Enabled` and `skipSmsToLandlines` false, `codeLength` 6): a returned value that differs is adopted, so `pulumi import --generate-code` includes it, and one that equals it stays out of the inputs, so an unchanged program still plans no change. The map is separate from the reset-on-removal defaults, so what an update sends for a removed input is unchanged. The entries come from the live report behind #1572 and are not yet re-probed per account (Twilio may differ by account or rollout); fields not in the map (`lookupEnabled`, ...) are still not adopted.
- Refresh no longer turns an explicitly empty list input into a missing one, which planned a permanent diff.

## [0.1.0] - 2026-11-04

### Added

- Add `qa.yaml`, the runtime test manifest QA reads: credentials, every resource and function with its test plan and cost, and the regressions to re-check. It is copied to the mirror root and changes no provider behavior.
- Lookup functions for every resource: `getSubaccount` (arg `subaccountSid`), `getApiKey` (`keySid`, optional `accountSid`; never returns the secret), `getApplication` (`applicationSid`, optional `accountSid`), `getMessagingService` and `getVerifyService` (`serviceSid`; results carry the configuration Twilio reports) and `getMessagingServicePhoneNumber` (`serviceSid`, `phoneNumberSid`). A missing object fails with "<object> was not found".
- `getBalance` reads the prepaid balance and currency of the provider account or a subaccount.
- Coverage inventory of Twilio's SDKs and OpenAPI definitions in `research/coverage/twilio.md`.

### Fixed

- `Subaccount` destroy of the provider's own top-level account is refused with a hint to run `pulumi state delete` to drop it from state.
- Preview no longer fails when a validated input is computed (for example a `friendlyName` built from another resource, or the `policy` of a restricted `ApiKey` that references a service created in the same stack): `Check` skips unknown values on `Subaccount`, `ApiKey`, `IncomingPhoneNumber`, `Application`, `MessagingService` and `VerifyService`.
- Removing a boolean or number input (`MessagingService` flags and `validityPeriod`, `VerifyService` flags and `codeLength`, `voiceCallerIdLookup`) is no longer silently mishandled: only inputs whose default is stated in Twilio's OpenAPI definitions are reset (`validityPeriod` to `36000`, `doNotShareWarningEnabled` to `false`); every other removed flag or number (`stickySender`, `useInboundWebhookOnNumber`, `codeLength`, `voiceCallerIdLookup` and so on) is left untouched on Twilio, because a reset to an unverified guess is worse than doing nothing. Import adopts every returned flag or number that has no documented default as an input.
- BREAKING: removing an HTTP method input (`voiceMethod`, `smsMethod`, `inboundMethod`, and the other `*Method` inputs) now sends `POST` instead of an empty string, which Twilio can reject.
- Refresh no longer echoes inputs: `Application`, `IncomingPhoneNumber`, `MessagingService` and `VerifyService` gain an `effective` output with the configuration Twilio reports (including console changes to fields the program does not set). Inputs the program leaves unset are never overwritten by server defaults.
- BREAKING: import now works for objects in a subaccount. `Application`, `IncomingPhoneNumber` and `ApiKey` created in a subaccount get the ID `<accountSid>/<sid>` (objects in the provider's own account keep the bare SID, and existing state keeps working). Importing an `ApiKey` from a subaccount sets `accountSid`, so a program that sets it no longer plans a replace.
- `ApiKey` in a subaccount: refresh, update and delete fall back to the account-explicit `/Accounts/{AccountSid}/Keys/{Sid}.json` route when the IAM route cannot see the key, so a subaccount key is no longer dropped from state on refresh and a delete no longer leaves a live credential behind. (Whether the IAM route actually scopes by account is not verified against a live account.)
- `IncomingPhoneNumber.accountSid` is no longer replace-on-change: a number is moved between accounts in place with Twilio's `AccountSid` update parameter (removing `accountSid` sends the number back to the provider account, so `protect` the resource). Previewing an update needs no credentials. BREAKING: changing `accountSid` used to plan a replace that always failed.
- `ApiKey` policy drift is detected: the policy is read back on refresh and compared as JSON on the keys the program supplied (extra fields Twilio echoes are not drift, and key order never matters, including in the subaccount-policy update check), so a restricted key widened in the console shows up as a diff and is restored by the next update. Import infers `keyType` and `policy`.
- `ApiKey` is created without a `KeyType` parameter for standard keys (`restricted` is sent only for restricted keys).
- `Subaccount` can no longer adopt or close the provider's own top-level account: import of it fails and destroy of it is refused.
- A failure after the object exists keeps it in state instead of leaking it: `Subaccount` created with `status: suspended` whose suspend call fails, and an `IncomingPhoneNumber` whose webhook configuration call fails, now return an initialization failure with the ID and partial state.
- README: the stored `ApiKey` policy is now read back, and import, subaccount IDs and removal semantics are documented.

- Initial native provider for Twilio (requested in #1412; Twilio has no maintained Terraform provider, so this is not a bridge).
- Resources: `Subaccount` (inputs `friendlyName`, `status`; outputs `sid`, secret `authToken`, `ownerAccountSid`, `dateCreated`; destroy closes the subaccount), `ApiKey` (inputs `friendlyName`, `accountSid`, `keyType`, `policy`; outputs `sid`, secret `secret`, `dateCreated`), `IncomingPhoneNumber` (adopts an owned number; inputs `phoneNumber` or `phoneNumberSid`, `accountSid`, `friendlyName`, voice and SMS webhooks and methods, fallbacks, status callback, `voiceApplicationSid`, `smsApplicationSid`, `voiceCallerIdLookup`; outputs `sid`, `number`, `ownerAccountSid`; never purchases or releases), `Application` (TwiML application webhooks; outputs `sid`, `ownerAccountSid`), `MessagingService` (webhooks, `stickySender`, `mmsConverter`, `smartEncoding`, `fallbackToLongCode`, `areaCodeGeomatch`, `synchronousValidation`, `useInboundWebhookOnNumber`, `scanMessageContent`, `validityPeriod`; output `sid`), `MessagingServicePhoneNumber` (inputs `serviceSid`, `phoneNumberSid`; outputs `phoneNumber`, `capabilities`) and `VerifyService` (inputs `friendlyName`, `codeLength`, `lookupEnabled`, `skipSmsToLandlines`, `dtmfInputRequired`, `ttsName`, `psd2Enabled`, `doNotShareWarningEnabled`, `customCodeEnabled`; output `sid`).
- Functions: `getAccount` (output `sid`, `friendlyName`, `status`, `type`, `ownerAccountSid`, `dateCreated`) and `getIncomingPhoneNumber` (by `phoneNumber` or `sid`).
- Provider config: `accountSid`, secret `authToken`, `apiKey`, secret `apiSecret`, `region`, `edge` and a testing-only `baseUrl`, each with a `TWILIO_*` environment fallback.
- Examples (messaging and subaccount scenarios in six languages) and `twilio-messaging` templates.
- Not validated against a live Twilio account; see README.
