# Changelog

## [Unreleased]

## [0.4.0] - 2026-11-12

### Added

- New Conversations resources `ConversationsService`, `ConversationsServiceConfiguration`, `ConversationsRole`, `ConversationsCredential`, `ConversationsAddressConfiguration` and `ConversationsWebhookConfiguration` and lookups `getConversationsService`, `getConversationsServiceConfiguration`, `getConversationsRole`, `getConversationsCredential`, `getConversationsAddressConfiguration` and `getConversationsWebhookConfiguration` (#1864, part of #1667): configure a Conversations service, its default roles and reachability, roles, push credentials (the certificate, keys and secret are secret inputs that Twilio never returns, so out-of-band changes to them are not detected), address configurations with auto-creation, and the webhook configuration (account-level, or of one service). A service cannot be renamed, so its `friendlyName` replaces it. The service configuration and the webhook configuration always exist, so they adopt the existing one and destroying them forgets it. A removed optional input leaves the Twilio setting unchanged. Import by SID (`<chatServiceSid>/<sid>` for a service role, the service SID for the two configurations, `account` for the account-level webhook configuration). Conversations, participants, messages, users and bindings are runtime data and are not managed; notification configuration and the account-level default configuration are left for a follow-up. Fake-server lifecycle tests only, nothing run against a live Twilio account.
- New TaskRouter resources `TaskRouterWorkspace`, `TaskRouterActivity`, `TaskRouterTaskChannel`, `TaskRouterTaskQueue`, `TaskRouterWorkflow` and `TaskRouterWorker` and lookups `getTaskRouterWorkspace`, `getTaskRouterActivity`, `getTaskRouterTaskChannel`, `getTaskRouterTaskQueue`, `getTaskRouterWorkflow` and `getTaskRouterWorker` (#1861, part of #1667): configure a TaskRouter workspace and its activities, task channels, task queues, workflows and workers. Import by `<workspaceSid>` or `<workspaceSid>/<sid>`. A workflow `configuration` and a worker `attributes` are compared as JSON documents, so reformatting is not a change. A worker's `activitySid` is applied on create and when you change it, and is never refreshed, because workers change activity while they work. A removed optional input leaves the Twilio setting unchanged. The workspace's `defaultActivitySid` and `timeoutActivitySid` are outputs only. Tasks, reservations, events and statistics are runtime data and are not managed.
- New resources `RoutesSipDomain`, `RoutesTrunk`, `RoutesPhoneNumber` and `RoutesShortCode` and lookups `getRoutesSipDomain`, `getRoutesTrunk`, `getRoutesPhoneNumber`, `getRoutesShortCode` (#1850, part of #1667): set the inbound voice or messaging processing region (and friendly name) of an existing SIP domain, SIP trunk domain, phone number or short code through Twilio Routes (routes.twilio.com). Settings update in place, the key inputs replace, import by key (`<isoCountryCode>/<shortCode>` for a short code). Twilio documents no way to unset a region, so destroy only forgets the setting. The superseded v2 phone number endpoint is not modelled. Additive, not breaking; mocked-HTTP tests only, shapes from twilio-oai Routes v2 and v3 (1.0.0).
- Read-only Pricing lookups (#1846, part of #1667): per-country price lists for Messaging (`getPricingMessagingCountry`: outbound per carrier and number type, inbound), Phone Numbers (`getPricingPhoneNumberCountry`), Voice (`getPricingVoiceCountry`, and `getPricingVoiceNumber` with an optional `originationNumber`) and Elastic SIP Trunking (`getPricingTrunkingCountry`, `getPricingTrunkingNumber`), each with a country list (`getPricingMessagingCountries`, `getPricingPhoneNumberCountries`, `getPricingVoiceCountries`, `getPricingTrunkingCountries`; every page is read). Prices are decimal strings as Twilio sends them. Voice and Trunking use the v2 API; the superseded v1 Voice pricing endpoints are not offered.

### Fixed

- `pulumi destroy` of a deployed Serverless Function no longer fails. Twilio has no delete for a `ServerlessDeployment`, refuses to delete a `ServerlessBuild` that a deployment points at (`Cannot delete Build because it's part of an active Deployment`, 400, error 20001) and then refuses to delete the `ServerlessFunction` or `ServerlessAsset` whose version the build holds (`...referenced in a Build`). A refused delete of a build, function or asset is now forgotten with a warning and the object stays on Twilio until its service is deleted; the message text is matched, so another 20001 is still an error. A build that was never deployed is still deleted. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/25 (#1856).
- Every resource with an HTTP method input (`Application`, `ConnectApp`, `EventSink`, `IncomingPhoneNumber`, `MessagingService`, `ShortCode`, `SipDomain`, `Trunk`, `UsageTrigger`, the Voice BYOC resources): `pulumi preview` no longer rejects a lower case method such as `voiceMethod: "post"` with `must be GET or POST`. Twilio takes either case, so Check accepts any case and normalizes the value to upper case; the request carries `POST` and the program plans no change against Twilio's `POST`. A value that is neither GET nor POST (any case) still fails. Nested callback `method` fields of the Voice v2 configurations are not changed. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/26 (#1857).

- `ServerlessBuild`: `pulumi preview` no longer fails with `functionVersionSids must hold version SIDs` when a version SID in the list is wired to another resource, such as `[${fnVersion.sid}]`. The element is unknown at preview and was checked as an empty string; an unknown element is now skipped and a known malformed one still fails. The same fix covers an unknown element of `assetVersionSids` and `dependencies`, `ConnectApp.permissions` and an unknown `EventSubscription` `types[].schemaVersion`. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/24 (#1855).

## [0.3.0] - 2026-11-11

### Added

- **VoiceDefaultRecordingConfiguration** and **VoiceDefaultTranscriptionConfiguration** resources and the lookups `getVoiceDefaultRecordingConfiguration` and `getVoiceDefaultTranscriptionConfiguration` (#1666): select which existing Voice v2 configuration is the account default (`POST /v2/Configurations/{Type}/Default` with `configuration_id`, read back with GET). Singleton per type, import by account SID; Twilio documents no call that unsets the default, so destroy only forgets the selection. The spec has no list endpoint for configurations, so no list lookups were added. Additive; fake-server tests only, unverified against a live account.
- The Serverless deploy plane (#1664): **ServerlessFunctionVersion**, **ServerlessAssetVersion**, **ServerlessBuild** and **ServerlessDeployment** resources and the lookups `getServerlessFunctionVersion`, `getServerlessAssetVersion`, `getServerlessBuild` and `getServerlessDeployment`, so `pulumi up` can deploy a Twilio Function end to end. The provider uploads code and files itself (multipart POST to `serverless-upload.twilio.com`; `content`, or `contentBase64` for binary assets), a `ServerlessBuild` takes the version SIDs (also ones made by the Twilio CLI or Serverless Toolkit), typed `dependencies` (`name`, `version`) and a `runtime`, and waits until Twilio reports it completed (a failed build is an error and is removed). A `ServerlessDeployment` points a `ServerlessEnvironment` at a build. Everything is immutable on Twilio's side, so every input replaces. Twilio has no delete for versions or deployments: destroying them only removes them from state (a build is deleted for real). Import IDs: `<serviceSid>/<functionSid or assetSid>/<sid>` for versions, `<serviceSid>/<sid>` for a build and `<serviceSid>/<environmentSid>/<sid>` for a deployment; an imported function version reads its code back, an imported asset version does not (Twilio does not return asset bytes). Additive, not breaking. Mocked-HTTP tests only; the upload host is not in the OpenAPI definitions, so its request shape follows the Twilio CLI and is not verified against a live account.
- Read-only lookups for the Voice dialing permissions (#1665): `getDialingPermissionsCountry` (one country by ISO code: low-risk, high-risk special services and high-risk toll fraud permissions, calling codes, continent), `getDialingPermissionsCountries` (the list, narrowed by ISO code, continent, calling code or any of the three permissions; every page is read) and `getDialingPermissionsHighRiskSpecialPrefixes` (the high-risk special services number prefixes of a country). No resource: Twilio changes these only through `POST /v1/DialingPermissions/BulkCountryUpdates`, whose own spec disagrees with itself on the wire format, so a write needs a live account first. A permission Twilio reports as null reads as false. Additive, not breaking; mocked-HTTP tests only, shapes from twilio-oai `twilio_voice_v1.json` 1.0.0.
- **VoiceAccountDefaultRecordingConfiguration** resource and the `getVoiceAccountDefaultRecordingConfiguration` lookup for the account-wide default Voice v2 recording configuration (`/v2/AccountDefaultConfiguration/Recording`, #1666). The inputs are those of a `VoiceRecordingConfiguration` without `uniqueName` (`description`, `compositionPolicy`, the two status callbacks and `features`), applied to calls that have no recording configuration of their own. It is a singleton: the resource ID and import ID is the account SID, creating it when a default already exists (409) replaces that default with the program's configuration, and destroying it removes the account default. Additive, not breaking. Mocked-HTTP tests only; shapes from twilio-oai `twilio_voice_v2.json` 0.0.1, not verified against a live account (the spec lists a 412 on ETag mismatch but documents no ETag header, so the provider sends none). The transcription default (`/Configurations/{Type}/Default`, which marks an existing configuration as the default by ID) is not covered.
- **VoiceRecordingConfiguration** and **VoiceTranscriptionConfiguration** resources and the lookups `getVoiceRecordingConfiguration` and `getVoiceTranscriptionConfiguration` for the Voice v2 configurations (`/v2/Configurations/Recording` and `/Transcription`, JSON bodies). Every input updates in place (PUT sends the whole configuration), import by configuration ID, `compositionPolicy`, callbacks, `features` and `participantDefaults` are typed objects with their enums checked at preview. Additive, not breaking; mocked-HTTP tests only, shapes from twilio-oai `twilio_voice_v2.json` (version 0.0.1, read 2026-11-09), not verified against a live account.

### Fixed

- The `adopt` doc comment in `provider/pkg/provider/props.go` now describes every import adopt rule, including the import-only default maps, the `Totp.Issuer` skip and list adoption (#1595). Comment only; no behavior change.
- The provider description, which becomes the Python package summary, is 223 characters instead of 603. PyPI rejects a summary over 512 characters, which failed the v0.2.0 Python publish (#1775). The Registry metadata check now fails any provider whose description or Python `packageDescription` is over 512 characters.
- Every resource with an HTTP method input (`Application` `voiceMethod`/`smsMethod`/`statusCallbackMethod`, `IncomingPhoneNumber`, `MessagingService`, `ShortCode`, `SipDomain`, the Voice BYOC and Trunk resources and the rest): a program that states the default (`voiceMethod: "POST"`) for an imported resource no longer plans an add of that method. An import does not adopt a returned POST (that keeps a program that omits the method clean), so the imported state had no method and the program's `POST` showed as a change that changes nothing on Twilio. An unset method and `POST` (any case) are now the same value; a real change (to or from `GET`, or removing `GET`) still plans an update. Nested method fields are not affected. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/21 (#1743).
- `VoiceRecordingConfiguration`: `pulumi preview` no longer fails with `featureId must not be empty` when a feature's `featureId` is wired to another resource, such as `${transcription.configurationId}` of a `VoiceTranscriptionConfiguration` in the same program. The value is unknown at preview and was checked as an empty string; an unknown `featureId` or feature `type` is now skipped, and a known empty one still fails. The same fix covers an unknown `participantDefaults[].type` or `audioChannelIndex` of `VoiceTranscriptionConfiguration`, an unknown `types[].type` of `EventSubscription` and an unknown element of `VerifyWebhook.eventTypes`, which all failed the same way when wired to another resource.
- `VerifyMessagingConfiguration`: creating one no longer stores a resource that does not exist. Twilio can answer the create request with HTTP 200 and a configuration for no country and a made-up Messaging Service SID, without creating anything; the resource was stored anyway and the next `pulumi refresh` dropped it from the state. The create now fails with an error that names what Twilio returned. A refresh after a successful create is unaffected. If your account hits this, the configuration cannot be created through the API for that Verify service and country.
- `pulumi import` of an object that does not exist (any resource: Address, ApiKey, Application, ConnectApp, EventSink, EventSubscription, IncomingPhoneNumber, MessagingService, OutgoingCallerId, Queue, ServerlessEnvironment, ShortCode, SigningKey, SipDomain, Subaccount, Trunk, UsageTrigger, VerifyService, the Voice BYOC and Verify resources and their children) now fails with an error instead of exiting 0 with an empty resource in state. Read returned the empty response that only a refresh treats as deleted. A refresh of a deleted object still drops it from state (#1715, same defect as #1712).
- `ServerlessEnvironment`: importing an environment created with a `domainSuffix` no longer plans a replacement (and with it a replacement of its variables) for the program that created it. An import now derives the suffix from the environment's domain name and the parent service's `domain_base` (`<domainBase>-<suffix>.twil.io`) and adopts it, except when it equals the unique name (Twilio's default suffix). When it cannot be derived, a program suffix that the recorded domain name already ends with is no change; a different suffix still replaces. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/18 (#1716).
- `VerifyMessagingConfiguration` and `getVerifyMessagingConfiguration`: a country without a configuration is no longer reported as existing. Twilio answers that GET with HTTP 200, an empty `country` and a made-up Messaging Service SID instead of 404; a response whose country is empty or differs from the requested one (case-insensitive) is now treated as not found. A refresh of a deleted configuration drops it from state, importing one that does not exist fails, and the lookup fails with `was not found` (it used to return the requested country with the made-up SID). Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/17 (#1717).

## [0.2.0] - 2026-11-08

### Fixed

- `SipDomain`: an import now adopts `sipRegistration: true`. A returned `true` was never adopted because the field had no known default, so the program that created the domain planned an update to set it. A returned `false` (a new domain) is still left out (#1572). The `false` default is the value a new domain reports; Twilio's spec states none. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/14 (#1680).
- `VerifyService`: an import now adopts `totpCodeLength`, `totpTimeStep` and `totpSkew` when they differ from Twilio's defaults (6, 30 and 1, as stated in the twilio_verify_v2 spec); default-valued ones stay out. Before, none were adopted and the program that created the service planned an update adding all three. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/15 (#1681).
- `UsageTrigger`: importing a trigger no longer adopts `triggerBy`, and the first preview of the program that created it no longer plans a replacement. Twilio always reports a `triggerBy` (it picks one from the usage category) and `triggerBy` replaces, so the adopted value made every program that never set it plan a delete and recreate. A new diff compares a program value with the value Twilio reports (new output `effectiveTriggerBy`): omitting `triggerBy` or stating Twilio's own pick is no change, a different value still replaces. Stating `callbackMethod: POST` after an import is no longer an update, and a reformatted `triggerValue` (`100` and `100.0`) is no longer a replacement. Additive output, not breaking. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/13 (#1679).
- Security: updated the indirect dependency `github.com/klauspost/compress` from v1.18.7 to v1.20.2, which fixes GO-2026-6865 (GHSA-fpmh-frq8-7rj8, a panic on two-block frames). No behaviour changes.
- `VerifyRateLimitBucket`: `Check` now rejects a `max` or `interval` of zero or less at preview time instead of leaving Twilio to reject it on apply. The spec states no upper bound, so none is enforced. Not breaking; mirrored provider, release follows the mirror.
- `VerifyService`: an import no longer adopts `totpIssuer`. Twilio sets the issuer to the friendly name at creation and keeps it when the service is renamed, so an imported stale issuer was adopted into the inputs, and because a removed `totpIssuer` is never sent (Twilio rejects an empty issuer) the program that omits it planned a change on every preview that could not be applied. A program that sets `totpIssuer` is an ordinary in-place update. Supersedes the 'a different value is still adopted' rule for this field. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/12 (#1658).
- `EventSink`: `webhookBatchEvents: true` no longer plans a replacement of the sink on every run. Twilio accepts `batch_events: true` on create but reports `false` afterwards, and a refresh copied that `false` into the inputs, so the next preview saw a change to a replace-on-change property. A refresh now keeps the recorded value, an import adopts only an explicit `true`, and `Create` logs a warning when Twilio does not echo `true`. The `webhookBatchEvents` description documents the behaviour. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/11 (#1657).
- `ServerlessVariable`: a refresh no longer replaces the recorded `value` with an empty string when Twilio omits the value from its response; the recorded value is kept.
- `SipCredential`: importing a credential no longer warns "One or more imported inputs failed to validate". Twilio never returns the password, so the imported inputs have an empty one and `Check` rejected it; an empty password is now accepted by `Check` (a non-empty one shorter than 12 characters still fails), while `Create` and `Update` refuse an empty password with `password must be set`. The in-place password update planned after an import is expected and documented. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/9 (#1635).
- `VerifyService`: removing `totpIssuer` from the program no longer fails with HTTP 400. Twilio sets the issuer to the friendly name at creation and rejects an empty value, so a removed input now leaves the issuer unchanged (like `defaultTemplateSid`); the description said it cleared the issuer. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/8 (#1633).
- Import no longer adopts Twilio's string defaults into the inputs: `MessagingService.usecase` equal to `undeclared` and `VerifyService.totpIssuer` equal to the friendlyName are left out, so `pulumi import` followed by `preview --expect-no-changes` plans nothing for a program that sets only the required fields. A different value is still adopted. The import-only map is separate from the update-reset maps. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/2 (#1634).
- `EventSink`: a Segment sink sent its write key as `key`, which Twilio rejects; it is now sent as `write_key` (and Twilio's `sink_configuration.write_key` is what a refresh reads). Twilio returns the webhook `method` in lower case (`post`), so a refresh and an import now read it as upper case and `webhookMethod` is compared case-insensitively: an imported default-method sink no longer adopts `webhookMethod: post` and a sink with a non-default method (`GET`) no longer plans a replacement after import. The test fake now rejects configuration keys unknown to the sink type and lower-cases the method like Twilio. Mirror issues https://github.com/pulumi-labs/pulumi-twilio/issues/6 and https://github.com/pulumi-labs/pulumi-twilio/issues/7 (#1631, #1632).
- If the provider schema cannot be loaded during a `Read`, the failure is no longer cached for the life of the process: the next `Read` retries (#1599). The lookup functions were audited: none returns a credential value, so no function output changes.

### Added

- New resource `IncomingPhoneNumberAssignedAddOn` assigns an installed Marketplace add-on (`installedAddOnSid`, `XE...`) to an incoming phone number (`phoneNumberSid`), with the lookup `getIncomingPhoneNumberAssignedAddOn` that also returns the add-on's read-only extensions. Twilio has no update call, so every input replaces the assignment. Twilio does not return the installation SID on read, so an imported assignment has an empty `installedAddOnSid` until the program sets it, which plans an in-place update that records it without calling Twilio. Import ID: `<phoneNumberSid>/<sid>` (`<accountSid>/<phoneNumberSid>/<sid>` on a subaccount's number). Not breaking; mirrored provider, release follows the mirror. Mocked-HTTP tests only; shapes from twilio-oai `twilio_api_v2010.json` (read 2026-11-06), not verified against a live account.
- New lookups `getAvailablePhoneNumbers`, `getUsageRecords`, `getAuthorizedConnectApps`, `getAuthorizedConnectApp`, `getEventTypes`, `getEventType` and `getEventSchema`. `getAvailablePhoneNumbers` takes `countryCode`, `numberType` (`local` default, `tollFree` or `mobile`), Twilio's search filters (`areaCode`, `contains`, `smsEnabled`, `mmsEnabled`, `voiceEnabled`, `faxEnabled`, `beta`, the `exclude...AddressRequired` flags, `inRegion`, `inPostalCode`, `inLocality`, `inRateCenter`, `inLata`, `nearNumber`, `nearLatLong`, `distance`) and a `limit` (default 50, at most 1000); it only searches and never buys. `getUsageRecords` takes an optional `period` (`allTime` default, `daily`, `monthly`, `yearly`, `today`, `yesterday`, `thisMonth`, `lastMonth`), `category`, `startDate`, `endDate`, `includeSubaccounts` and `limit`; `price`, `count` and `usage` stay the decimal strings Twilio sends. `getAuthorizedConnectApps` lists and `getAuthorizedConnectApp` reads by `connectAppSid` the Connect Apps an account authorized. `getEventTypes` (optional `schemaId`), `getEventType` (`type`) and `getEventSchema` (`schemaId`, with every published version) expose the Event Streams catalogue. Pages are followed through `next_page_uri` and `meta.next_page_url`; a list still continuing after 100 pages is an error, never a silent truncation.

- New resources `ByocTrunk`, `ConnectionPolicy`, `ConnectionPolicyTarget`, `IpRecord` and `SourceIpMapping` for Bring Your Own Carrier on the Voice API (voice.twilio.com), with lookups `getByocTrunk`, `getConnectionPolicy`, `getConnectionPolicyTarget`, `getIpRecord` and `getSourceIpMapping`. A `ByocTrunk` manages its name, voice, fallback and status callback URLs and methods, `cnamLookupEnabled`, `connectionPolicySid` and `fromDomainSid`; everything updates in place, and removing a URL or SID input clears it on Twilio. A `ConnectionPolicy` holds `ConnectionPolicyTarget` carrier targets (`target` must be a `sip:` URI; `priority` and `weight` default to 10 and `enabled` to true; everything but `connectionPolicySid` updates in place). An `IpRecord` is an IPv4 address with an optional `cidrPrefixLength` (default 32); both replace, `friendlyName` updates in place. A `SourceIpMapping` maps an `IpRecord` to a `SipDomain` (`ipRecordSid` replaces, `sipDomainSid` updates in place). Import IDs: the SID, or `<connectionPolicySid>/<sid>` for a target; an import adopts defaults-valued settings only when they differ from Twilio's defaults. Dialing permissions and the recording and transcription configurations are not managed. Not breaking; mirrored provider, release follows the mirror. Mocked-HTTP tests only; shapes from twilio-oai `twilio_voice_v1.json` (spec version 1.0.0, read 2026-11-06), not verified against a live account.

- New resources `ServerlessService`, `ServerlessEnvironment`, `ServerlessVariable`, `ServerlessFunction` and `ServerlessAsset` for the configuration plane of Twilio Serverless (serverless.twilio.com), with lookups `getServerlessService`, `getServerlessEnvironment`, `getServerlessVariable`, `getServerlessFunction` and `getServerlessAsset`. A service's `friendlyName`, `includeCredentials` and `uiEditable` update in place and its `uniqueName` replaces; leaving a flag unset keeps what Twilio holds. Twilio has no update call for an environment, so every input (`uniqueName`, `domainSuffix`, `serviceSid`) replaces it. A variable's `key` and `value` update in place and `value` is a Pulumi secret. `ServerlessFunction` and `ServerlessAsset` manage the container (`friendlyName` updates in place); the code or file inside is uploaded as an immutable version through Twilio's upload host, which the OpenAPI definitions do not describe, so versions, builds and deployments are not managed (deploy with the Serverless Toolkit or the Twilio CLI). Import IDs: service by SID (`ZS...`), environment and function or asset as `<serviceSid>/<sid>`, variable as `<serviceSid>/<environmentSid>/<sid>`. Not breaking; mirrored provider, release follows the mirror. Mocked-HTTP tests only; shapes from twilio-oai `twilio_serverless_v1.json` (spec version 1.0.0, read 2026-11-06), not verified against a live account.

- New resources `VerifyRateLimit`, `VerifyRateLimitBucket`, `VerifyMessagingConfiguration`, `VerifyWebhook` and `VerifySafeListNumber` for Twilio Verify v2, with lookups `getVerifyRateLimit`, `getVerifyRateLimitBucket`, `getVerifyMessagingConfiguration`, `getVerifyWebhook`, `getVerifySafeListNumber` and `getVerifyTemplates` (lists the message templates, optional exact `friendlyName`; use a returned `sid` as `VerifyService.defaultTemplateSid`). A rate limit's `description`, a bucket's `max` and `interval`, a configuration's `messagingServiceSid` and a webhook's `friendlyName`, `eventTypes`, `webhookUrl`, `status` and `webhookVersion` update in place; `serviceSid`, `rateLimitSid`, `uniqueName` and `country` replace, and a SafeList entry replaces on any change. Twilio's webhook `Version` is the input `webhookVersion`. The order of `eventTypes` is not significant, and an imported webhook adopts `status` and `webhookVersion` only when they differ from Twilio's defaults (`enabled`, `v2`). Not breaking; mirrored provider, release follows the mirror. Mocked-HTTP tests only; shapes from twilio-oai `twilio_verify_v2.json` (spec version 1.0.0, read 2026-11-06), not verified against a live account.

- New resources `Trunk`, `TrunkOriginationUrl`, `TrunkCredentialList` and `TrunkIpAccessControlList` for Elastic SIP Trunking (trunking.twilio.com), with lookups `getTrunk`, `getTrunkOriginationUrl`, `getTrunkCredentialList` and `getTrunkIpAccessControlList`. A `Trunk` manages `domainName` (`<name>.pstn.twilio.com`), `friendlyName`, the disaster recovery URL and method, `transferMode`, `transferCallerId`, `secure`, `cnamLookupEnabled` and the recording settings `recordingMode` and `recordingTrim` (applied through Twilio's Recording sub-resource); everything updates in place and the `effective` output shows what Twilio holds. A `TrunkOriginationUrl` (`sipUrl` must be a `sip:` URL; `weight` and `priority` default to 10, `enabled` to true) updates in place and only `trunkSid` replaces it. `TrunkCredentialList` and `TrunkIpAccessControlList` attach an existing `SipCredentialList` or `SipIpAccessControlList`; Twilio has no update call, so every input replaces, and destroy only detaches. Trunks belong to the credentials' account (no `accountSid`). Phone numbers keep being attached with `IncomingPhoneNumber.trunkSid`. Import IDs: `Trunk` by SID, the others as `<trunkSid>/<sid>`; an imported trunk adopts only settings that differ from Twilio's defaults, so omitting a setting or stating its default plans no change. Shapes follow twilio-oai `twilio_trunking_v1.json`; mocked-HTTP tests only.

- New resources `EventSink` and `EventSubscription` for Twilio Event Streams, with lookups `getEventSink` and `getEventSubscription` (both by `sid`). A sink is a `webhook` (`webhookDestination`, `webhookMethod`, `webhookBatchEvents`), `kinesis` (`kinesisArn`, `kinesisRoleArn`, `kinesisExternalId`) or `segment` (`segmentWriteKey`) destination; only its `description` updates in place and every other input replaces, because Twilio's API cannot change a sink's configuration. `segmentWriteKey` and `kinesisExternalId` are secrets, and Twilio does not return the write key, so drift in it is not detected. A subscription takes a `description`, a `sinkSid` (replaces) and a list of `types` (`type`, optional `schemaVersion`); types are added, re-versioned and removed in place through the SubscribedEvents endpoints, and a refresh picks up types changed outside Pulumi. Twilio only creates a subscription for an active sink: a new sink must be validated first (Twilio's sink test and validate calls, which are not part of the provider). Import by SID; an imported sink never replaces because of a setting Twilio does not return (the Segment write key, a missing Kinesis external ID) or states as a default (`webhookMethod` `POST`, `webhookBatchEvents` false); an imported subscription pins the schema version of every type. Shapes follow twilio-oai `twilio_events_v1.json`; mocked-HTTP tests only.

- New resources `ShortCode` (SMS webhooks, `friendlyName`, `apiVersion` of a leased short code), `ConnectApp` (listing details and `permissions` of a Console-created Connect app) and `OutgoingCallerId` (the `friendlyName` of a verified caller ID), with lookups `getShortCode` (by `code` or `sid`), `getConnectApp` and `getOutgoingCallerId` (by `phoneNumber` or `sid`). Shapes follow twilio-oai `twilio_api_v2010.json` (`SMS/ShortCodes`, `ConnectApps`, `OutgoingCallerIds`); mocked-HTTP tests only.

The legacy `Domains/{sid}/CredentialListMappings` paths are not used: they alias the `Auth/Calls` mappings. Shapes follow twilio-oai `twilio_api_v2010.json`; mocked-HTTP tests only.

### Fixed

- Security: `pulumi import` and `pulumi refresh` now store the properties this provider marks secret (`ApiKey.secret`, `SigningKey.secret` and `Subaccount.authToken`) as secrets. A `Read` response only kept the secretness of the state it was given, and an import has no state, so a value the provider recovered from the API was written to the state as plaintext. The secret properties are read from the provider's own schema, so every resource is covered. State imported before this fix stays plaintext until its next `pulumi refresh`, which re-encrypts it (#1577).
- A preview no longer invents resource IDs. `Create` during `pulumi preview` returned the resource's logical name (or the placeholder `preview`) as its ID, so `id` was a known, wrong value and a program passing it to a lookup or to another resource ran against a name that does not exist and failed the preview (for example `getWebhook(webhook.id)`). A preview has no real ID now, so `id` stays unknown until the apply. Mirror issue https://github.com/pulumi-labs/pulumi-huggingface/issues/7 (#1590).
- Changing the provider configuration (a rotated token, API key or secret, a new endpoint or region) is an in-place update of the default provider. By default pulumi-go-provider replaced the provider on any config change, and replacing a provider replaces every resource that uses it, so rotating a credential would have deleted and recreated every resource. Each resource's own diff still decides whether it changes. Mirror issue https://github.com/pulumi-labs/pulumi-huggingface/issues/8 (#1591).
- `ApiKey`: the documented restricted-key policy was not a policy Twilio accepts. `{"allow":["/v1/Services/**"]}` (the schema description, SKILLS.md and, as `/v2/Services/**`, the six `twilio-subaccount` examples) fails with error 70002; Twilio only takes assertions of the form `/twilio/<product>/<resource>/<action>`, and the verified example is now `{"allow":["/twilio/iam/api-keys/create"]}` everywhere. Check logs a warning for an assertion that does not start with `/twilio/`.
- `ApiKey`: a failed create no longer leaves an untracked key. Twilio creates the key and then fails the call with 70002, and the error carries no SID, so the key was a live credential Pulumi did not know about. Create now notes the account's keys before the call and, on failure, deletes the key that is new and carries this resource's friendly name (never a key that existed before); if the keys cannot be listed (including an account with more keys than the 10 pages it reads) or the key cannot be deleted, the error says so and names what to look for. Every `ApiKey` create now costs one extra key listing, and a failed create removes keys of its friendlyName created during the call, so keep friendlyNames unique among keys created in one program. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/4 (#1574).
- Previewing an update no longer makes identifiers unknown. A preview that only renamed a `Subaccount` marked its `sid`, `ownerAccountSid` and auth token unknown, so every resource reading `${sub.sid}` into its `accountSid` (which replaces) was planned for replacement, although the real update is in place; replacing a subaccount `ApiKey` would have lost its one-time secret, so the preview misled anyone reviewing it. Every resource now declares what its outputs derive from: identifiers fixed at creation (`sid`, `ownerAccountSid`, `dateCreated`, `secret`, `authToken`, ...) stay known on update, while what Twilio reports and can change (`effective`, queue counters, address validation, usage values) stays unknown. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/3 (#1573).
- Import no longer adopts Twilio's own defaults as inputs. `Application`, `MessagingService`, `VerifyService` (and every other resource that adopts on import) copied each returned flag or number into the inputs unless its default was verified, so `pulumi import` followed by a program that set only `friendlyName` planned to remove `voiceCallerIdLookup`, `stickySender`, `codeLength`, `psd2Enabled` and the like, and failed `--expect-no-changes`. A flag or number is now adopted only when Twilio's OpenAPI states its default and the returned value differs from it; the others stay out of the inputs and remain visible in the `effective` output. Trade-off: this also leaves out a genuine non-default setting of such a field (for example `codeLength: 4` or `stickySender: false`), so `pulumi import --generate-code` omits it; the setting is still shown in `effective`, and declaring it in the program is an ordinary in-place update that sends the declared value. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/2 (#1572).
- Import now adopts a non-default flag or number even when Twilio's OpenAPI states no default (#1595). An import-only default map holds the values a fresh resource reports on the live API (`voiceCallerIdLookup` false, `stickySender`, `areaCodeGeomatch`, `mmsConverter`, `smartEncoding` and `dtmfInputRequired` true, `synchronousValidation`, `useInboundWebhookOnNumber`, `customCodeEnabled`, `psd2Enabled` and `skipSmsToLandlines` false, `codeLength` 6): a returned value that differs is adopted, so `pulumi import --generate-code` includes it, and one that equals it stays out of the inputs, so an unchanged program still plans no change. The map is separate from the reset-on-removal defaults, so what an update sends for a removed input is unchanged. The entries come from the live report behind #1572 and are not yet re-probed per account (Twilio may differ by account or rollout); fields not in the map (`lookupEnabled`, ...) are still not adopted.
- Refresh no longer turns an explicitly empty list input into a missing one, which planned a permanent diff.

## [0.1.0] - 2026-11-04

### Added

- Add `qa.yaml`, the runtime test manifest QA reads: credentials, every resource and function with its test plan and cost, and the regressions to re-check. It is copied to the mirror root and changes no provider behavior.

A missing object fails with "<object> was not found".

- Coverage inventory of Twilio's SDKs and OpenAPI definitions in `research/coverage/twilio.md`.

### Fixed

- `Subaccount` destroy of the provider's own top-level account is refused with a hint to run `pulumi state delete` to drop it from state.
- Preview no longer fails when a validated input is computed (for example a `friendlyName` built from another resource, or the `policy` of a restricted `ApiKey` that references a service created in the same stack): `Check` skips unknown values on `Subaccount`, `ApiKey`, `IncomingPhoneNumber`, `Application`, `MessagingService` and `VerifyService`.
- Removing a boolean or number input (`MessagingService` flags and `validityPeriod`, `VerifyService` flags and `codeLength`, `voiceCallerIdLookup`) is no longer silently mishandled: only inputs whose default is stated in Twilio's OpenAPI definitions are reset (`validityPeriod` to `36000`, `doNotShareWarningEnabled` to `false`); every other removed flag or number (`stickySender`, `useInboundWebhookOnNumber`, `codeLength`, `voiceCallerIdLookup` and so on) is left untouched on Twilio, because a reset to an unverified guess is worse than doing nothing. Import adopts every returned flag or number that has no documented default as an input.
- BREAKING: removing an HTTP method input (`voiceMethod`, `smsMethod`, `inboundMethod`, and the other `*Method` inputs) now sends `POST` instead of an empty string, which Twilio can reject.
- Refresh no longer echoes inputs: `Application`, `IncomingPhoneNumber`, `MessagingService` and `VerifyService` gain an `effective` output with the configuration Twilio reports (including console changes to fields the program does not set). Inputs the program leaves unset are never overwritten by server defaults.
- BREAKING: import now works for objects in a subaccount. `Application`, `IncomingPhoneNumber` and `ApiKey` created in a subaccount get the ID `<accountSid>/<sid>` (objects in the provider's own account keep the bare SID, and existing state keeps working). Importing an `ApiKey` from a subaccount sets `accountSid`, so a program that sets it no longer plans a replace.
- `ApiKey` in a subaccount: refresh, update and delete fall back to the account-explicit `/Accounts/{AccountSid}/Keys/{Sid}.json` route when the IAM route cannot see the key, so a subaccount key is no longer dropped from state on refresh and a delete no longer leaves a live credential behind. (Whether the IAM route actually scopes by account is not verified against a live account.)
- `IncomingPhoneNumber.accountSid` is no longer replace-on-change: a number is moved between accounts in place with Twilio's `AccountSid` update parameter (removing `accountSid` sends the number back to the provider account, so `protect` the resource). Previewing an update needs no credentials. BREAKING: changing `accountSid` used to plan a replace that always failed.
- `ApiKey` policy drift is detected: the policy is read back on refresh and compared as JSON on the keys the program supplied (extra fields Twilio echoes are not drift, and key order never matters, including in the subaccount-policy update check), so a restricted key widened in the console shows up as a diff and is restored by the next update. Import infers `keyType` and `policy`.
- `ApiKey` is created without a `KeyType` parameter for standard keys (`restricted` is sent only for restricted keys).
- `Subaccount` can no longer adopt or close the provider's own top-level account: import of it fails and destroy of it is refused.
- A failure after the object exists keeps it in state instead of leaking it: `Subaccount` created with `status: suspended` whose suspend call fails, and an `IncomingPhoneNumber` whose webhook configuration call fails, now return an initialization failure with the ID and partial state.
- README: the stored `ApiKey` policy is now read back, and import, subaccount IDs and removal semantics are documented.

- Initial native provider for Twilio (requested in #1412; Twilio has no maintained Terraform provider, so this is not a bridge).
