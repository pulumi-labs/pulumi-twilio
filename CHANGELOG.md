## [0.6.0] - 2026-11-13

### Security

- Security: updated OpenTelemetry (`go.opentelemetry.io/otel`, `sdk`, `trace`, `metric`, `log` and the OTLP trace exporters) from 1.45.0 to 1.47.0, which fixes GHSA-q7gw-24fr-5p69 (CVE-2026-128085, `AttributeValueLengthLimit` bypass in opentelemetry-go, vulnerable 1.33.0 to 1.46.x). Clears the pulumi-labs/pulumi-twilio Dependabot alerts for it once released (part of #1966). Not breaking.

### Fixed

- `pulumi destroy`, refresh and updates of an imported resource now use credentials and endpoints given only through environment variables (#1955, same root cause as #1951): after `pulumi import` the engine reconfigures the provider without running the config defaults (upstream pulumi/pulumi-go-provider#527), so the environment fallbacks were skipped; the provider config now fills unset settings from the environment in `Configure`. Not breaking.
- `VideoCompositionHook` (#1937): the next preview after a refresh no longer plans an update of `videoLayout`. Twilio reports its defaults for every region of a layout (an empty `cells_excluded` and `video_sources_excluded`, `reuse` `show_oldest`, `x_pos`, `y_pos` and `z_pos` 0, null `height`, `width`, `max_rows` and `max_columns`); Read and Diff now compare layouts with those defaults removed from both sides, from one table, and the state keeps the program's own form. A non-default value changed in the program or outside Pulumi still shows. Import adopts the layout without the defaults. State an earlier release wrote with the expanded layout plans no change. `TaskRouterWorker.attributes` and `TaskRouterWorkflow.configuration` use the same JSON comparison but Twilio echoes them as written, so they were not changed. Regression test: the fake server is made to return the expanded layout. Not breaking.

## [0.5.0] - 2026-11-13

### Changed

- Internal only, no behavior change (#1896): each Twilio default that import adoption (Read) and Diff both rely on now lives in one table per resource, so the two can no longer disagree. A test fails when a Read default has no Diff counterpart. Not breaking.

### Fixed

- `ConversationsAddressConfiguration` Check now names the nested property in a failure inside `autoCreation` (`autoCreation.type`, `autoCreation.conversationServiceSid`, `autoCreation.webhookMethod`) instead of reporting it against `autoCreation` (#1899, part of #1667). Message text only; the same values are accepted and refused. Not breaking.
- Imported Conversations, Notify and Sync resources no longer plan a spurious in-place update when the program writes a Twilio default explicitly (#1888, the same defect #1880 fixed for TaskRouter). Affected: `NotifyService` (`logEnabled`, `deliveryCallbackEnabled`, credential and URL fields), `NotifyCredential` and `ConversationsCredential` (`sandbox`), `SyncService` (`reachabilityDebouncingWindow` 5000 and the reachability, ACL and webhook flags), `ConversationsConfiguration`, `ConversationsServiceConfiguration`, `ConversationsServiceNotificationConfiguration`, `ConversationsWebhookConfiguration` and `ConversationsAddressConfiguration` (including the `autoCreation` object, `addressCountry` and `friendlyName`). Diff now reads an unset stored value as the same default that import leaves unset. The nested notification settings of `ConversationsServiceNotificationConfiguration` (`newMessage`, `addedToConversation`, `removedFromConversation`) read an unset stored value as disabled with empty text. A non-default value still plans a change. Not breaking. A single defaults table shared by Read and Diff is tracked in #1896.
- Imported TaskRouter resources no longer plan changes (or, for `TaskRouterActivity`, a replacement) when the program sets a Twilio default explicitly (#1880, mirror pulumi-labs/pulumi-twilio#31). An import leaves an input unset when Twilio's value is the default, and Diff treated that unset value as different from the default, so `available: true` on an imported activity replaced it. Diff now reads an unset stored value as the default for every TaskRouter property that has one: `TaskRouterActivity.available` (true), `TaskRouterWorkspace` (`multiTaskEnabled` false, `prioritizeQueueOrder` FIFO, empty callback URL and events filter), `TaskRouterTaskChannel.channelOptimizedRouting` (false), `TaskRouterTaskQueue` (`targetWorkers` 1==1, `maxReservedWorkers` 1, `taskOrder` FIFO, empty activity SIDs), `TaskRouterWorkflow` (`taskReservationTimeout` 120, empty callback URLs) and `TaskRouterWorker.attributes` (`{}`). A non-default value still plans its change. A worker's `activitySid` is still not refreshed on import, so setting it in the program after an import plans an in-place update. The same defect remains in the Conversations, Notify and Sync resources that share the Diff helper (for example `NotifyService.logEnabled` and `SyncService.reachabilityDebouncingWindow`); it is a spurious update there, not a replace, and is tracked in #1888, so this fix is not complete for the whole provider. Not breaking.
- `ServerlessAssetVersion` no longer warns on import (#1879, mirror pulumi-labs/pulumi-twilio#30): Check required exactly one of `content` and `contentBase64`, but Twilio never returns asset bytes, so the inputs an import produces have neither. Check now only rejects setting both; creating a version with neither still fails (at create, not at preview) because there is nothing to upload. `ServerlessFunctionVersion` is unaffected: its code is read back on import. Not breaking.
- `ServerlessBuild` import and `getServerlessBuild` now see the function and asset versions and no longer plan a replacement after an import (#1878, mirror pulumi-labs/pulumi-twilio#28 and #29). Twilio returns `function_versions` and `asset_versions` as objects, and only plain strings were read, so the SID lists came back empty. The SIDs are now read from the `sid` of each object (plain strings still work). `dependencies` are compared without regard to order and Twilio's own default packages (`util`, `xmldom`, `lodash`, `@twilio/runtime-handler`) that an imported build lists are ignored when the program does not name them; a changed or missing listed dependency still replaces. Not breaking.

### Fixed

- `pulumi destroy` of a deployed Serverless Function no longer fails. Twilio has no delete for a `ServerlessDeployment`, refuses to delete a `ServerlessBuild` that a deployment points at (`Cannot delete Build because it's part of an active Deployment`, 400, error 20001) and then refuses to delete the `ServerlessFunction` or `ServerlessAsset` whose version the build holds (`...referenced in a Build`). A refused delete of a build, function or asset is now forgotten with a warning and the object stays on Twilio until its service is deleted; the message text is matched, so another 20001 is still an error. A build that was never deployed is still deleted. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/25 (#1856).
- Every resource with an HTTP method input (`Application`, `ConnectApp`, `EventSink`, `IncomingPhoneNumber`, `MessagingService`, `ShortCode`, `SipDomain`, `Trunk`, `UsageTrigger`, the Voice BYOC resources): `pulumi preview` no longer rejects a lower case method such as `voiceMethod: "post"` with `must be GET or POST`. Twilio takes either case, so Check accepts any case and normalizes the value to upper case; the request carries `POST` and the program plans no change against Twilio's `POST`. A value that is neither GET nor POST (any case) still fails. Nested callback `method` fields of the Voice v2 configurations are not changed. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/26 (#1857).

- `ServerlessBuild`: `pulumi preview` no longer fails with `functionVersionSids must hold version SIDs` when a version SID in the list is wired to another resource, such as `[${fnVersion.sid}]`. The element is unknown at preview and was checked as an empty string; an unknown element is now skipped and a known malformed one still fails. The same fix covers an unknown element of `assetVersionSids` and `dependencies`, `ConnectApp.permissions` and an unknown `EventSubscription` `types[].schemaVersion`. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/24 (#1855).

## [0.3.0] - 2026-11-11

### Added

- **VoiceDefaultRecordingConfiguration** and **VoiceDefaultTranscriptionConfiguration** resources and the lookups `getVoiceDefaultRecordingConfiguration` and `getVoiceDefaultTranscriptionConfiguration` (#1666): select which existing Voice v2 configuration is the account default (`POST /v2/Configurations/{Type}/Default` with `configuration_id`, read back with GET). Singleton per type, import by account SID; Twilio documents no call that unsets the default, so destroy only forgets the selection. The spec has no list endpoint for configurations, so no list lookups were added. Additive; fake-server tests only, unverified against a live account.
- The Serverless deploy plane (#1664): **ServerlessFunctionVersion**, **ServerlessAssetVersion**, **ServerlessBuild** and **ServerlessDeployment** resources and the lookups `getServerlessFunctionVersion`, `getServerlessAssetVersion`, `getServerlessBuild` and `getServerlessDeployment`, so `pulumi up` can deploy a Twilio Function end to end. The provider uploads code and files itself (multipart POST to `serverless-upload.twilio.com`; `content`, or `contentBase64` for binary assets), a `ServerlessBuild` takes the version SIDs (also ones made by the Twilio CLI or Serverless Toolkit), typed `dependencies` (`name`, `version`) and a `runtime`, and waits until Twilio reports it completed (a failed build is an error and is removed). A `ServerlessDeployment` points a `ServerlessEnvironment` at a build. Everything is immutable on Twilio's side, so every input replaces. A `Read` response only kept the secretness of the state it was given, and an import has no state, so a value the provider recovered from the API was written to the state as plaintext. By default pulumi-go-provider replaced the provider on any config change, and replacing a provider replaces every resource that uses it, so rotating a credential would have deleted and recreated every resource. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/4 (#1574).
- Previewing an update no longer makes identifiers unknown. A preview that only renamed a `Subaccount` marked its `sid`, `ownerAccountSid` and auth token unknown, so every resource reading `${sub.sid}` into its `accountSid` (which replaces) was planned for replacement, although the real update is in place; replacing a subaccount `ApiKey` would have lost its one-time secret, so the preview misled anyone reviewing it. Every resource now declares what its outputs derive from: identifiers fixed at creation (`sid`, `ownerAccountSid`, `dateCreated`, `secret`, `authToken`, ...) stay known on update, while what Twilio reports and can change (`effective`, queue counters, address validation, usage values) stays unknown. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/3 (#1573).
- Import no longer adopts Twilio's own defaults as inputs. `Application`, `MessagingService`, `VerifyService` (and every other resource that adopts on import) copied each returned flag or number into the inputs unless its default was verified, so `pulumi import` followed by a program that set only `friendlyName` planned to remove `voiceCallerIdLookup`, `stickySender`, `codeLength`, `psd2Enabled` and the like, and failed `--expect-no-changes`. A flag or number is now adopted only when Twilio's OpenAPI states its default and the returned value differs from it; the others stay out of the inputs and remain visible in the `effective` output. Trade-off: this also leaves out a genuine non-default setting of such a field (for example `codeLength: 4` or `stickySender: false`), so `pulumi import --generate-code` omits it; the setting is still shown in `effective`, and declaring it in the program is an ordinary in-place update that sends the declared value. Mirror issue https://github.com/pulumi-labs/pulumi-twilio/issues/2 (#1572).
- Import now adopts a non-default flag or number even when Twilio's OpenAPI states no default (#1595). An import-only default map holds the values a fresh resource reports on the live API (`voiceCallerIdLookup` false, `stickySender`, `areaCodeGeomatch`, `mmsConverter`, `smartEncoding` and `dtmfInputRequired` true, `synchronousValidation`, `useInboundWebhookOnNumber`, `customCodeEnabled`, `psd2Enabled` and `skipSmsToLandlines` false, `codeLength` 6): a returned value that differs is adopted, so `pulumi import --generate-code` includes it, and one that equals it stays out of the inputs, so an unchanged program still plans no change. The map is separate from the reset-on-removal defaults, so what an update sends for a removed input is unchanged. The entries come from the live report behind #1572 and are not yet re-probed per account (Twilio may differ by account or rollout); fields not in the map (`lookupEnabled`, ...) are still not adopted.
- Refresh no longer turns an explicitly empty list input into a missing one, which planned a permanent diff.

## [0.1.0] - 2026-11-04

### Added

- Add `qa.yaml`, the runtime test manifest QA reads: credentials, every resource and function with its test plan and cost, and the regressions to re-check. It is copied to the mirror root and changes no provider behavior.
- Lookup functions for every resource: `getSubaccount` (arg `subaccountSid`), `getApiKey` (`keySid`, optional `accountSid`; never returns the secret), `getApplication` (`applicationSid`, optional `accountSid`), `getMessagingService` and `getVerifyService` (`serviceSid`; results carry the configuration Twilio reports) and `getMessagingServicePhoneNumber` (`serviceSid`, `phoneNumberSid`). A missing object fails with "<object> was not found".
- `getBalance` reads the prepaid balance and currency of the provider account or a subaccount.
- Coverage inventory of Twilio's SDKs and OpenAPI definitions in `research/coverage/twilio.md`.

### Fixed

- `Subaccount` destroy of the provider's own top-level account is refused with a hint to run `pulumi state delete` to drop it from state.
- Preview no longer fails when a validated input is computed (for example a `friendlyName` built from another resource, or the `policy` of a restricted `ApiKey` that references a service created in the same stack): `Check` skips unknown values on `Subaccount`, `ApiKey`, `IncomingPhoneNumber`, `Application`, `MessagingService` and `VerifyService`.
- Removing a boolean or number input (`MessagingService` flags and `validityPeriod`, `VerifyService` flags and `codeLength`, `voiceCallerIdLookup`) is no longer silently mishandled: only inputs whose default is stated in Twilio's OpenAPI definitions are reset (`validityPeriod` to `36000`, `doNotShareWarningEnabled` to `false`); every other removed flag or number (`stickySender`, `useInboundWebhookOnNumber`, `codeLength`, `voiceCallerIdLookup` and so on) is left untouched on Twilio, because a reset to an unverified guess is worse than doing nothing. Import adopts every returned flag or number that has no documented default as an input.
- BREAKING: removing an HTTP method input (`voiceMethod`, `smsMethod`, `inboundMethod`, and the other `*Method` inputs) now sends `POST` instead of an empty string, which Twilio can reject.
- Refresh no longer echoes inputs: `Application`, `IncomingPhoneNumber`, `MessagingService` and `VerifyService` gain an `effective` output with the configuration Twilio reports (including console changes to fields the program does not set). Inputs the program leaves unset are never overwritten by server defaults.
- BREAKING: import now works for objects in a subaccount. `Application`, `IncomingPhoneNumber` and `ApiKey` created in a subaccount get the ID `<accountSid>/<sid>` (objects in the provider's own account keep the bare SID, and existing state keeps working). Importing an `ApiKey` from a subaccount sets `accountSid`, so a program that sets it no longer plans a replace.
- `ApiKey` in a subaccount: refresh, update and delete fall back to the account-explicit `/Accounts/{AccountSid}/Keys/{Sid}.json` route when the IAM route cannot see the key, so a subaccount key is no longer dropped from state on refresh and a delete no longer leaves a live credential behind. (Whether the IAM route actually scopes by account is not verified against a live account.)
- `IncomingPhoneNumber.accountSid` is no longer replace-on-change: a number is moved between accounts in place with Twilio's `AccountSid` update parameter (removing `accountSid` sends the number back to the provider account, so `protect` the resource). Previewing an update needs no credentials. BREAKING: changing `accountSid` used to plan a replace that always failed.
- `ApiKey` policy drift is detected: the policy is read back on refresh and compared as JSON on the keys the program supplied (extra fields Twilio echoes are not drift, and key order never matters, including in the subaccount-policy update check), so a restricted key widened in the console shows up as a diff and is restored by the next update. Import infers `keyType` and `policy`.
- `ApiKey` is created without a `KeyType` parameter for standard keys (`restricted` is sent only for restricted keys).
- `Subaccount` can no longer adopt or close the provider's own top-level account: import of it fails and destroy of it is refused.
- A failure after the object exists keeps it in state instead of leaking it: `Subaccount` created with `status: suspended` whose suspend call fails, and an `IncomingPhoneNumber` whose webhook configuration call fails, now return an initialization failure with the ID and partial state.
- README: the stored `ApiKey` policy is now read back, and import, subaccount IDs and removal semantics are documented.

- Initial native provider for Twilio (requested in #1412; Twilio has no maintained Terraform provider, so this is not a bridge).
- Resources: `Subaccount` (inputs `friendlyName`, `status`; outputs `sid`, secret `authToken`, `ownerAccountSid`, `dateCreated`; destroy closes the subaccount), `ApiKey` (inputs `friendlyName`, `accountSid`, `keyType`, `policy`; outputs `sid`, secret `secret`, `dateCreated`), `IncomingPhoneNumber` (adopts an owned number; inputs `phoneNumber` or `phoneNumberSid`, `accountSid`, `friendlyName`, voice and SMS webhooks and methods, fallbacks, status callback, `voiceApplicationSid`, `smsApplicationSid`, `voiceCallerIdLookup`; outputs `sid`, `number`, `ownerAccountSid`; never purchases or releases), `Application` (TwiML application webhooks; outputs `sid`, `ownerAccountSid`), `MessagingService` (webhooks, `stickySender`, `mmsConverter`, `smartEncoding`, `fallbackToLongCode`, `areaCodeGeomatch`, `synchronousValidation`, `useInboundWebhookOnNumber`, `scanMessageContent`, `validityPeriod`; output `sid`), `MessagingServicePhoneNumber` (inputs `serviceSid`, `phoneNumberSid`; outputs `phoneNumber`, `capabilities`) and `VerifyService` (inputs `friendlyName`, `codeLength`, `lookupEnabled`, `skipSmsToLandlines`, `dtmfInputRequired`, `ttsName`, `psd2Enabled`, `doNotShareWarningEnabled`, `customCodeEnabled`; output `sid`).
- Functions: `getAccount` (output `sid`, `friendlyName`, `status`, `type`, `ownerAccountSid`, `dateCreated`) and `getIncomingPhoneNumber` (by `phoneNumber` or `sid`).
- Provider config: `accountSid`, secret `authToken`, `apiKey`, secret `apiSecret`, `region`, `edge` and a testing-only `baseUrl`, each with a `TWILIO_*` environment fallback.
- Examples (messaging and subaccount scenarios in six languages) and `twilio-messaging` templates.
- Not validated against a live Twilio account; see README.
